Requirements, contract and decisions live in the source-of-truth PRD (§5 FR-1.1, FR-1.2, FR-1.9, FR-1.10, FR-1.11, FR-4.6; §6; §7; D19). This repo builds **Console › Messaging**: the ops work queue, every store's MSG91 account, the message rates and (FR-4.6) the stores' prepaid message balances and top-up requests, on the platform-admin API (`messaging.schema.ts`).

## Decisions recorded here

- **D19 (owner, 2026-11-27, "Go a-head with all this phase"), Phase 1 console note:** the console never creates an MSG91 account by itself and never switches sending on. "Create messaging account" asks for an explicit per-store confirmation that the owner said yes; sending on/off is shown read-only with a note that it is the backend `messaging-email-move` CLI with the owner's per-store yes. The add_client API switch carries a warning and a confirm dialog: it stays off until MSG91 confirms the API in writing (FR-0.2).

## UX notes (this repo)

- **Where:** a **Messaging** item in the black menu after Support (`/messaging`, icon Mail), visible with `platform:messaging:read`; underline tabs kept in `?tab=` (Work queue default, `accounts`, `rates`, and since FR-4.6 `balances`, `top-ups`). The console feed's MESSAGING_TASK_NEW rows (category STORES) link to `/messaging`; the Stores tab of the bell now also opens with `platform:messaging:read`.
- **Work queue:** status tabs Open · Done · Rejected · All (server-side; Open shows the server's `openCount`), a task-type filter, the line "N open · N overdue", and one card per task: type and store, the domain (`subject`), where it came from, when it was opened, the SLA chip (overdue red, due within 4 hours amber, else grey "Due in …"), the status chip, the step's hint, every value with a copy button (`aria-label` "Copy <label>"), and for closed tasks the note or reject reason. Actions (manage only, open tasks): **Done** opens the per-type form (CREATE_CHILD the child's MSG91 id; ADD_EMAIL_DOMAIN a repeatable DNS-records form: type, purpose, host relative or full, value, required, MX priority, up to 12; VERIFY_EMAIL_DOMAIN a confirm checkbox; every type an optional note ≤ 500), **Reject** asks for the reason, and a CONNECT_CHILD task also has **Connect account**, which reads the store's account and opens the connect form. Server paging (20 a page).
- **Accounts:** state tabs All · Connected · Problem · Creating · Not created; a table with store and kind (child id), state chip (MSG91's failure message under Problem, else when it was last checked), credentials saved in words ("Auth key saved · No SMTP login"; never a value), sending domain and its verification, sending On/Off (read-only). Manage only: **Create messaging account** and **Connect existing account** in the toolbar (store picker from the loaded stores), and per row Create account / Connect / Update credentials.
- **Create messaging account:** the store, an info line (with the add_client API off it opens a Create task with every value to copy; on, ZCOM creates the child now), mobile with country code and optional company name only while the API is on, and a required "The owner said yes to an MSG91 account for <store>" checkbox.
- **Connect / update credentials:** kind, child id, auth key (password input), send mode (SMTP: host, port, username, password (password input); HTTP API: the template id), "mail.zerrorstudios.com is verified in this account". The key and password are never prefilled, are cleared from the form on every submit and when the pop-up closes, and are never shown again (the API returns only `hasAuthKey` / `hasSmtpLogin`). Blank fields keep what is saved. The answer's state decides the message: ACTIVE closes with "passed its check. Sending stays off."; FAILED stays open with MSG91's message.
- **Rates:** a channel × purpose table (Email, SMS, WhatsApp × Marketing, Transactional, Service) typed in rupees (two decimals, ≤ ₹10,000) and sent as integer paise, only the changed channels (a change is a new version; version, date and who are shown); the add_client switch with its warning; Save / Discard (manage only; read-only inputs otherwise).
- **Balances (FR-4.6):** filter tabs All stores · Low only (`lowOnly`: stores warned LOW or EMPTY), server paging (20 a page), lowest first as the server sorts. Columns: store (last update), available, balance, held for sends, last top-up, level chip (Empty red, Low amber, OK green). Money is integer paise on the wire and shown as ₹ with two decimals (₹0.00 for zero). A row opens a drawer with the four figures, the **ledger** (when, movement label: Top-up, Grant, Correction, Held for a send, Send settled, Charged; reason and who; signed amount, or the held amount for a reserve; balance after; server paging 20 a page) and the store's latest **top-ups** with their actions. **Grant or correct** (manage only; row button and drawer header): a Grant (add) / Correction (remove) switch, the amount in rupees (above zero, two decimals at most, up to ₹1,00,000; a correction at most what's available, i.e. not held for a send), a required reason (≤ 500, kept in the ledger and audit log), then a **confirm step** with the balance now and after; Back returns to the form. Sent as signed whole paise.
- **Top-up requests (FR-4.6):** status tabs Waiting for payment (default) · Paid · Withdrawn · All, server paging; columns request number and date, store and who asked, amount, status, payment (paid date, provider, reference). Manage only, PENDING rows: **Record payment** (required bank transfer reference ≤ 200; the server credits the balance) and **Withdraw** (required reason ≤ 500; the balance is unchanged). Read-only roles see the lists without buttons.
- **Errors:** branches on `extensions.code` / `reason` only. `INVALID_INPUT`, `INVALID_DNS_RECORD`, `INVALID_RATE`, `REASON_REQUIRED` land on the field named by `extensions.field` (`childId`, `records.N.host`, `rates.SMS.MARKETING`, `mobile`, `smtpPort`…); `SAMPLE_STORE`, `ALREADY_CONNECTED`, `MESSAGING_ACCOUNT_NOT_READY`, `TASK_CLOSED` get console copy (TASK_CLOSED closes the pop-up and the queue reloads); `MSG91_REFUSED` shows the server's message (it carries MSG91's code). FR-4.6: `INVALID_AMOUNT` (field `amountPaise`) lands on the amount, `REASON_REQUIRED` on `reason` or `reference` (a server refusal of the confirm step returns to the form with the field error); `TOPUP_NOT_PENDING` gets console copy, closes the pop-up and the lists reload.
- **States:** skeletons while loading, an error with Retry, empty states per tab and filter, success toasts.
- **Usage check (D20, FR-1.11; `?tab=reconciliation`, `?month=YYYY-MM`, `?status=`):** a summary card for the month (stores checked, how many differ, ZCOM sent, MSG91 logged; "Run again" for the whole month with `platform:messaging:manage`), status tabs All · Differs · MSG91 error · Matches · No data, a month picker (the server's `months`, latest first), server paging. Rows: account (store, or "Zerror (parent account)" with "Shared-address mail sent through Zerror's account"; a store that also mailed through its own SMTP says how many), status chip (Differs red, MSG91 error amber, Matches green, No MSG91 data grey) with the server's short error, ZCOM sent with the purpose split, MSG91 logged, difference (+/− and %, red when it differs), when it was checked and the tries, and "Check again" per store (manage). The bell's MESSAGING_USAGE_MISMATCH rows link here with the month.
- **Feed alerts (D20):** MESSAGING_TOPUP_REQUESTED (WARNING, `/messaging?tab=top-ups`), MESSAGING_BALANCE_EMPTY (CRITICAL, `/messaging?tab=balances`) and MESSAGING_USAGE_MISMATCH (WARNING) arrive in the bell's Stores tab with `platform:messaging:read`; the panel renders every kind generically (title, body, severity tone, console link), so no client change was needed beyond the tab they open.
- **KYC and hourly limits (D21, MSG91's written answers; backend §5 "D21 as built"):** Accounts gain a "KYC · limit" column (KYC chip: not started / with MSG91 / approved / rejected, and the account's emails an hour) and a "KYC and limit" dialog per account (`platform:messaging:manage`): MSG91's KYC state with a note (required when rejected; the store sees it) via `setMessagingAccountKyc`, and the hourly email limit (500 to start; raise only when MSG91 has) via `setMessagingHourlyEmailLimit`, each sent only when changed. The queue shows the new **MSG91 KYC** task type (Done records approval, Reject records the refusal). Rates gains an "Hourly email limits" card: Zerror's parent account's emails an hour and marketing's share of each hour (10–100 %, with the resulting marketing emails at 500 an hour), saved through `updatePlatformMessagingSettings`. `KYC_NOT_APPROVED` has its own toast. The accounts banner says sending is switched on only after KYC is approved.

- **Parent row, automatic top-up (D22; backend §5 "D22 marketing and billing gaps as built"):** the Usage check's parent line now reads "Shared address from N stores … · Zerror's own mail …" (`parentSources`: every store's shared-address mail, whatever its account's state, plus Zerror's own platform mail, which goes through the parent SMTP); its status, difference and feed alert work as for a store. Top-up requests name an automatic one "Automatic (balance under the store's threshold)"; the store drawer on Balances says whether the store's automatic top-up is on, with its threshold and amount (read-only; the store sets it). The console feed's top-up alert says "auto top-up requested" for those. Nothing in the console charges a store.
