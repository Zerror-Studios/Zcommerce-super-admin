## UX notes (this repo)

- The store page is the two-pane section card since 2026-10-28 (`e4ce936`; one section per URL, `/stores/:id/:section`): the PRD's "Profile card", "History section" and "Health card" are placed as **Store › Profile** (its own section, `/profile`), **Insights › History** (its own section, `/history`), the **Store health signals** card beside the GA4 card in **Insights › Analytics**, and the **Billing state** card at the top of **Billing › Billing & plan**. The header's payment-app chip sits beside the status and payment chips. (Before the restyle, 2026-10-16 owner note, they were cards in one long main column.)
- The PRD-025 fields are read by **one extra query per store** (`PlatformTenantProfile`) and never added to the shared `PlatformTenantFields` fragment: `PlatformTenants` reads that fragment for every store and sits near the gateway cost limit (2026-10-27 fix, cost ~1850 of 5000). The Profile, History and Billing state cards and the header chip share the one read through `hooks/use-tenant-profile.ts` (Apollo cache).
- Profile edits **in place** (Edit turns the rows into fields; Save / Cancel in the card header), not in a modal like Store details, per §6 "inline edit with Save".
- Dates use the kit's `formatDate` / `formatDateTime` like the rest of the console; the planned go-live date is edited as the UTC day (`YYYY-MM-DD`) and sent as that string.
- Permission: the PRD names `platform:tenants:write` for the profile edit. That permission doesn't exist in `platform-permissions.ts`; the backend guards `updateTenant` with `platform:tenants:manage`, so the console gates the Edit button on **manage** (UX only; the server decides).
- Not built (no FR-6 screen asks for them): `platformWebhookHealth`, `platformMrrHistory(includeTenants: true)`.
